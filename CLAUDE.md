# SGM Stereo: Arm Optimisation Benchmark

## Mission

Find out how fast Semi-Global Matching can be made to run on Arm application
cores and GPU silicon, without ever being wrong. Every implementation here runs
the *same* algorithm with the *same* parameters and must produce a
*bit-identical* disparity map to the scalar reference. Then we report MDE/s,
per-core throughput, and perf/W where a board exposes a usable rail.

The deliverable is a table, not a demo. Every number in it must come from a
run logged in `results/`, never from an estimate.

## Workload definition (single source of truth: `common/sgm_params.h`)

| Parameter | Value | Status |
|---|---|---|
| Resolution | 1920 x 1080 | fixed |
| Disparity range D | 64 | fixed (128 also benchmarked) |
| Aggregation paths | 4 | fixed (L, R, U, D) |
| Cost | 9x7 census (62-bit, centre skipped) + Hamming | fixed |
| P1 / P2 | 20 / 192 | P2 capped so Cmax + P2 <= 255 (8-bit L) |
| Path cost L | uint8 with per-pixel renormalisation (`- min_k L[k]`) | fixed |
| Path sum S | uint16 | fixed |
| Disparity | integer argmin, lowest-d wins ties | fixed |
| LR check / subpixel / median | OFF | fixed |
| Border handling | disparity 0, cost 63 where x-d < 0 | fixed |

Cost is proportional to `D x paths`. If either changes, **every**
implementation is rebuilt and re-run; there is no scaling of old numbers.

`sgm_params.h` is the only place these live. No implementation hardcodes D,
window size, or penalties. Changing a parameter and rebuilding must be a
one-line edit.

## Boards (confirm cpu ids on first boot of each)

| Column | Board | Cores under test | Notes |
|---|---|---|---|
| A55 | i.MX 95 EVK | 6x Cortex-A55 @ 1.8 GHz | also hosts the Mali G310 |
| A720 | Radxa Orion O6 (CIX P1) | Cortex-A720 cluster(s) only | pin away from the A520s; log which A720 cluster (there are two at different clocks) |
| Small GPU | i.MX 95 Mali-G310 | OpenCL if the BSP ships an ICD, else Vulkan compute | low priority; record "no driver" as a result if that's the answer |
| Mid GPU (bonus) | Orion O6 Immortalis-G720 | OpenCL | only after G310 is done or declared dead |
| Big GPU | Skippy, RTX 5090 | CUDA via Fixstars libSGM | the credibility anchor; do not hand-write CUDA |

Identify cores by MIDR, not by cpu number:
`cat /sys/devices/system/cpu/cpu*/regs/identification/midr_el1` — part
numbers: A55 = 0xd05, A520 = 0xd80, A720 = 0xd81. Build the `taskset` mask
from that, and print the mask and the current frequency of every core in the
mask at the start of each run.

### How an implementation plugs in

Implement `sgm_run_fn` (see `common/sgm.h`), export `const sgm_impl SGM_IMPL`,
add it to `IMPLS` in the Makefile. The harness does everything else. Run:

```
make MCPU=cortex-a55 golden          # once per parameter set, on any machine
source scripts/pin.sh
pin_run a55 6 ./bin/sgm_a55 data/synthetic/left.pgm data/synthetic/right.pgm \
    -g data/golden/synthetic.pgm -t 6 -j results/imx95.json --board imx95
```

Exit code 2 means the output did not match golden. That run is void.

## Ground rules

1. **Bit-exact or it doesn't count.** `sgm_ref.c` produces the golden map.
   Every implementation's output must be byte-identical to the golden map (the harness compares pixels and prints FNV-1a; `make golden` also records sha256) for the
   same parameter set, on both the synthetic and the real pair. The GPU
   paths too — this is integer arithmetic, there is no excuse for drift.
   If libSGM's tie-breaking differs, document the exact rule and add a
   matching oracle mode rather than waving it through.

2. **Measure the whole pipeline.** fps = one rectified pair in, one disparity
   map out. Census, Hamming, aggregation, argmin all inside the timer. Report
   per-stage ms as well, but the headline is end-to-end.

3. **No cost volume in DRAM.** A line-buffered design streams and
   never writes `W x H x D` bytes anywhere. A 1080p x 64 cost volume is 133
   MB; writing it turns the A55 column into an LPDDR benchmark. Compute
   Hamming cost on the fly inside the aggregation sweep from the census
   descriptors (2 x 1080p x 8 bytes = 33 MB, read-only, prefetch-friendly).
   Materialising the cost volume is allowed only in `sgm_ref.c`.

4. **Pin everything.** `OMP_PLACES=cores OMP_PROC_BIND=close` plus the
   `taskset` mask from `pin.sh`. Governor = performance. Log the actual
   frequency of every pinned core at run start and run end; if they differ
   by more than 2%, the run is thermally throttled and gets flagged.

5. **Measurement protocol.** 10 warm-up frames, then 100 timed frames,
   report median and p95. Run at thread counts 1, 2, 4, 6 (A55) and 1, 2, 4
   (A720 big cluster). Capture `perf stat -e cycles,instructions,
   L1-dcache-load-misses,l2d_cache_refill` on the timed frames for the CPU
   columns.

6. **Power.** i.MX 95 EVK: use the PMIC rail monitors if exposed via hwmon,
   else an inline USB-C power meter, idle-subtracted. O6: inline meter.
   5090: `nvidia-smi --query-gpu=power.draw --format=csv -lms 100` averaged
   over the timed window. Report W and Mpix/s/W; if power can't be measured
   on a board, leave the cell blank rather than estimating.

7. **Compiler.** GCC 13+, `-O3 -mcpu=cortex-a55` / `-mcpu=cortex-a720`
   (not `-march=native`, so the flags are reproducible). No `-ffast-math`
   (irrelevant, integer code, but don't). Record compiler version and flags
   in every results JSON.

## Phases

Each phase ends with a results JSON committed and the golden hash matched.
Do not start the next phase with a hash mismatch outstanding.

### Phase 0 — Harness and oracle (scaffold done; you run it)
- Oracle, harness, generator, Makefile and pin.sh exist and are tested
  (oracle hits 98.9% exact vs synthetic ground truth in the interior, and
  the golden compare path correctly flags mismatches with exit code 2).
- Generate golden ANYWHERE (deterministic scalar C), VERIFY on the board: `make golden`
  then re-run on the i.MX 95 and diff the sha256. A mismatch is a compiler or
  endianness bug and must be understood before anything is built on it.
  If Kyle has put a real pair in `data/real/`, golden is produced for it too.
- Run `./scripts/pin.sh` alone on each board and paste its output into
  `results/topology_<board>.txt`. Fix the board table above if it's wrong.
- Run the two baselines on the i.MX 95 at 1, 2, 4, 6 threads via `pin_run`
  and record their output in `results/baseline_imx95.txt`. They use their
  own random data and are not bit-exact (row paths only) — that's fine,
  they are the "before" number. Expected: ~4 Mpix/s equivalent on 6 threads.
- Check the oracle's own throughput at 1080p on the A55 (expect ~0.3 Mpix/s,
  single thread). It's the floor, not a data point.

### Phase 1 — Common NEON kernels
- Census 9x7 in NEON: sliding-window compare against centre, `vcgtq_u8`,
  bit-pack with `vshlq`/`vorrq` into a uint64 per pixel. Target: memory-bound.
- Hamming cost in NEON: for fixed x the 64 right descriptors are a
  contiguous reversed run. `veorq_u64` + `vcntq_u8` + `vpaddlq_u8`, narrow
  to uint8. Expose as an inline function callable from inside the
  aggregation sweep, not as a separate pass.
- Both must produce identical output to their scalar versions.

### Phase 2 — A55 (in-order, 128-bit NEON, ~1 vector op/cycle)
- 8-bit aggregation: D=64 x uint8 = four `uint8x16_t` registers per path
  direction. Keep all four in registers across the pixel step.
- `vqaddq_u8` for +P1 / +P2 so 0xff sentinels can't wrap.
- d-1 / d+1 via `vextq_u8` across adjacent registers (same trick as the
  existing uint16 code, twice the lanes).
- Fold `min_k` into the write pass: `vminq_u8` accumulate during output,
  one `vminvq_u8` per pixel per direction, off the critical chain.
- Two sweeps: forward (L, U, UL, UR) and backward (R, D, DL, DR). Each sweep
  keeps the previous row's L for the three vertical/diagonal paths in a
  `W x D` buffer per direction — 123 KB each at 1080p/D=64, so tile the row
  into column strips that keep the working set inside the A55's L2.
  Accumulate the 4 path costs into the uint16 S row as you go. Second sweep
  adds to S and does the argmin.
- Thread over row *strips* for the horizontal-ish sweep and over column
  strips for the vertical dependency; measure both decompositions, keep the
  faster. The vertical paths serialise across rows, so the parallel axis
  must be columns for those — this is the part that costs threading
  efficiency, and the number that comes out is the real one.
- Check IPC with `perf stat`. A55 tops out near 2.0; if aggregation is
  below ~1.3, look at load-use stalls and reorder loads earlier by hand.
- Done when: bit-exact, 6-thread fps recorded, per-core Mpix/s recorded,
  IPC recorded. Target order of magnitude: 12-16 Mpix/s on 6 cores.

### Phase 3 — A720 (out-of-order, 4x 128-bit SIMD pipes)
- Start from the A55 kernel, rebuild with `-mcpu=cortex-a720`, measure.
  That's the "naive port" number; keep it.
- The recurrence is a ~5-op dependency chain per pixel per direction. One
  scanline cannot fill four pipes. Interleave K independent scanlines in
  the same loop body (K = 2, 3, 4 — measure each). Register budget:
  4 regs x K rows x (L + neighbours) — K=4 fits in the 32 NEON registers
  only if the temporaries are tight; check the disassembly for spills.
- Confirm with `perf stat` that IPC rises with K. If it doesn't, the loop
  is memory-bound and the fix is prefetch, not ILP.
- SVE2 at VL=128 offers no lane gain over NEON; only try it if a specific
  instruction (e.g. `match`, `histcnt`) removes real work. Default: don't.
- Report per-core Mpix/s for each A720 cluster separately (they clock
  differently).
- Done when: bit-exact, best K recorded, naive-port vs interleaved recorded.

### Phase 4 — Mali-G310 (i.MX 95) via OpenCL
- First check: `clinfo`. If there is no ICD, check the BSP for
  `libmali` with OpenCL, then Vulkan compute (`vulkaninfo`). If none of
  those exist, record "no compute driver available in BSP <version>" as the
  result for this column and move on. Do not spend more than a day here.
- Kernel design: one work-group per scanline per direction, 16 work-items
  each holding a `uchar4` (4 disparities) — matches Valhall's 16-wide warp
  so `sub_group_reduce_min` gives min_k in one op. d-1 / d+1 across
  work-items via `sub_group_shuffle` (or local memory if the extension is
  missing). Census + Hamming as a separate kernel writing descriptors; the
  aggregation kernel reads descriptors and computes cost in-register.
- Expected: it loses to 4x A720. Report it anyway.
- Bonus: same kernels on the O6's Immortalis-G720 if time permits.

### Phase 5 — RTX 5090 via libSGM
- Build https://github.com/fixstars/libSGM with CUDA on Skippy. Configure
  `disp_size` = D, `path_type` = 4, census 9x7
  (libSGM's default), P1/P2 from `sgm_params.h`, `subpixel = false`,
  `LR_max_diff = -1` (disables LR check).
- Wrap it in the same harness so the timing and hashing are identical.
- Verify bit-exactness against the golden map. If ties break differently,
  document the rule and match it in the oracle; do not accept "close".
- Record fps, Mpix/s, power from `nvidia-smi`, and SM count so Mpix/s/SM
  can be reported.

### Phase 6 — Report
`scripts/report.py` reads `results/*.json` and emits:

| Platform | Cores/threads | Clock | fps @1080p | Mpix/s | MDE/s | Mpix/s per core | W | Mpix/s per W |

Per-core rates use the *best* observed at any thread count. Power is left
blank rather than estimated on boards with no usable rail.

## What not to do

- Don't tune on the synthetic pair only. Real image statistics change
  branch behaviour in the scalar code and cache behaviour everywhere.
- Don't quote a number from a run whose output hash didn't match.
- Don't let OpenMP pick cores. On the O6 it will happily put threads on the
  A520s and the A720 number will be wrong.
- Don't compare implementations run with different D or path counts. Ever.
- Don't hand-write CUDA. libSGM is the bar and it is already good.
- Don't spend more than a day on the G310 driver situation.
- Don't round up the software numbers. The point of the exercise is that
  they are small.
